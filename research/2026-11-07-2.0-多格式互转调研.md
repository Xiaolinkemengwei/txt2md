# 2.0 多格式互转：开源方案调研

- 调研日期：2026-11-07
- 调研对象：txt2md v1.0.0（`D:\github\txt2md`）
- 目的：为 2.0「任意两格式双向转换」寻找可复用且可合法分发的方案
- 证据层级：**1 = 源码/元数据核查（未运行）**，**2 = 局部实测**，**3 = 集成验证**，**4 = 不采用/待验证**

---

## 1. 项目基线（以源码核实）

| 项 | 现状 |
|---|---|
| 核心 | `txt2md.py`：`read_text_smart`（BOM→UTF-8→Big5→GBK）、`smart_line`/`to_markdown`（保守排版）、`convert_file`、`collect_txt_files` |
| 依赖 | 命令行：**零第三方依赖**；界面：`PySide6-Essentials>=6.6` |
| 界面 | `gui/`（Fluent 2 亮色），`ConvertWorker(QThread)` 逐文件跑 `convert_file` |
| 分发 | PyInstaller 单文件 exe（35.8 MB）+ wheel；MIT |
| 现有转换能力 | 只有一条固定的边：`txt → md`（外加 `--plain`） |

**缺口**：格式维度只有 1 条边，且方向单一。2.0 要做的是把「1 条边」变成「N×N 有向图」，并且不能破坏 1.0 的零依赖命令行、编码探测、批量与非中断语义。

## 3. 关键实测（证据层级 2）

环境：Windows 11，隔离 venv（`build/exp/venv`），`pypandoc_binary` 1.17 自带 **pandoc 3.9**，`openpyxl` 3.1.5，`xlsxwriter`。

| # | 用例 | 命令要点 | 结果 |
|---|---|---|---|
| 1 | pandoc 格式统计 | `pandoc --list-input-formats` / `--list-output-formats` | 输入 **51** 种、输出 **75** 种；`xlsx` 只在输入侧，`pdf` 只在输出侧 |
| 2 | md → docx | `convert_file(a.md, "docx", outputfile=a.docx)` | **OK**，10,936 B |
| 3 | docx → md（往返） | `convert_file(a.docx, "gfm")` | **OK**，标题/粗体/列表/表格结构完整还原 |
| 4 | md → html | 同上 | **OK**，263 B |
| 5 | md → txt | `to="plain"` | **OK**，101 B |
| 6 | txt → docx | `format="markdown"` | **OK**，10,444 B |
| 7 | md → pdf | `to="pdf"` | **FAIL**：`pdflatex not found. Please select a different --pdf-engine` |
| 8 | md → xlsx | `to="xlsx"` | **FAIL**：`Invalid output format!`（pandoc 无 xlsx 写出） |
| 9 | xlsx → md（openpyxl 生成） | `to="gfm"` | **FAIL**：`Failed to parse XLSX: Entry not found: xl//xl/worksheets/...` |
| 10 | xlsx → md（xlsxwriter 生成） | 同上 | **OK**：`## 数据` + 表格，但数值 90 → `90.0` |
| 11 | Edge headless：html → pdf | `msedge --headless --print-to-pdf` | **OK**：`%PDF-1.4`，45,928 B，2 页 |

**第 9/10 条是本轮最有价值的发现**：pandoc 的 xlsx 读取对生成器敏感——同一个逻辑表格，xlsxwriter 生成的能读，openpyxl 生成的一律报路径错误。这意味着**不能把 xlsx 交给 pandoc**，必须自己用 openpyxl 读写。

**第 7、11 条共同决定 PDF 方案**：pandoc 输出 PDF 只是「转交排版引擎」，缺 LaTeX 就失败；而系统自带的 Edge 能把 html 打成结构完好的 PDF，零安装成本。

## 4. 逐个裁决

### 4.1 pandoc —— 采用为「可选引擎」（证据层级 2）

- **解决的本地问题**：docx / odt / pptx / epub / html / rst / org 等文本格式的读写，自研不现实（仅 docx 的 OOXML 样式映射就是数千行）。
- **接入方式**：`subprocess` 调用独立进程，**不捆绑二进制**。GPL-2.0 的义务只作用于「分发 pandoc 本体」；以独立进程调用、用户自行安装，则不传染本项目的 MIT 代码。
- **必须改造的点**：① 路径探测（PATH / `pypandoc_binary` / 用户指定）；② 调用超时与 stderr 归因；③ 输出格式名映射（`md`→`gfm`/`markdown`，`txt`→`plain`）；④ **不调用 xlsx、不调用 pdf 输出**。
- **不能照搬**：上游没有「引擎缺失」的降级设计，缺引擎时直接异常——本项目需要在启动时探测并灰化不可达目标格式。

### 4.2 LibreOffice headless —— 采用为「可选引擎」（证据层级 1）

- **解决的本地问题**：docx/xlsx/pptx → pdf 的**版式保真**，这是唯一现实路径（pandoc 与 Edge 都做不到）。
- **接入方式**：探测 `soffice.exe`（PATH、`C:\Program Files\LibreOffice\program`、绿色版目录），`-env:UserInstallation` 指向临时目录以避免并发锁。
- **不能照搬**：不把它打进 exe（安装后 500 MB+，且 MPL-2.0 的分发义务复杂）；缺失时降级到 Word COM → 再失败则明确提示。
- 本机**未安装**，因此该项只有源码/文档级判断，未做实测（证据层级 1）。

### 4.3 Edge / Chromium headless —— 采用为 PDF 输出首选（证据层级 2）

- **解决的本地问题**：md/txt/html → pdf 零安装可达，且中文字体由系统处理。
- **接入方式**：`--headless --disable-gpu --print-to-pdf=<abs> <file:///abs.html>`；探测 Edge → Chrome → Chromium 顺序。
- **限制**：只吃 HTML，所以 md/txt 要先经 pandoc（或自研）转 html；无页码/页眉控制之外的高级排版能力。

### 4.4 markitdown —— 不采用（证据层级 1）

- 只做 **→ Markdown**，与「双向」目标直接冲突；即使采用也只能覆盖一半方向。
- 39 项依赖（`magika`、`onnxruntime` 一类）会把单文件 exe 从 35 MB 推到 150 MB 量级。
- 官方自述「面向 LLM 消费，**不是高保真人工转换**」，与桌面工具定位不符。
- 可借鉴：它对「表格 → Markdown 表格」的降级策略值得抄进自研 xlsx 编码器。

### 4.5 gotenberg —— 不采用（证据层级 1）

- 出口**只有 PDF**，多格式互转的核心诉求它只满足「→ pdf」一列。
- 要求用户运行 Docker，与「解压即用」的发布形态冲突。
- 可借鉴：它的路由划分（chromium / libreoffice / pdfengines）与我们的「引擎适配器」思路一致，佐证了架构方向。

### 4.6 pdf2docx / PyMuPDF —— 不采用（证据层级 1）

- `pdf2docx` 自身 MIT，但依赖 **PyMuPDF（AGPL-3.0 或商业授权）**。一旦打进 exe 并在 GitHub 分发，等于把整个程序拖进 AGPL 义务。
- 因此 **PDF → DOCX 的「版式还原」不进入 2.0 内置能力**，只提供「文本层重排」的降级结果，并在界面上明示保真等级。

### 4.7 pdfplumber —— 采用（证据层级 1）

- MIT、纯 Python，`pdfminer.six` 派生，能拿文本与表格线框。
- 定位：**只读**。用于 pdf → txt/md 的文本层提取，扫描件（无文本层）明确不支持。

---

## 5. 结论

1. **不存在**一个能同时满足「任意格式双向 + 可合法打进单文件 exe + 中文环境」的现成项目。gotenberg 最接近但出口单一，markitdown 方向单一。
2. 正确的复用姿势是**组合**：自研轻量编解码（txt/md/html/csv/xlsx）+ 可选外部引擎（pandoc / LibreOffice / Edge / Word）+ 文本层读取（pdfplumber）。
3. 真正需要「复用」的复杂部分只有两类：**OOXML 样式映射**（交给 pandoc）与 **office→pdf 版式排版**（交给 LibreOffice/Word）。这两块自研都是数月级工作量。
4. 许可红线：**不引入 PyMuPDF 系（AGPL）**；pandoc 只以独立进程调用，不捆绑二进制。
