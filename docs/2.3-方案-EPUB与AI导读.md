## 二、EPUB：为什么自己写而不用 ebooklib

### 选型对比

| 方案 | 体积 | 许可 | 控制力 | 结论 |
|---|---|---|---|---|
| `ebooklib` | + 依赖链（lxml、six） | AGPL-3.0 | 高 | **否**，AGPL 与本项目 MIT 不兼容 |
| `pypandoc` 走 pandoc | +231 MB 的 pandoc 二进制 | GPL | 中 | 否，为一个格式装 231 MB 不值 |
| 标准库 zipfile + xml | 0 | — | 完全 | **采用** |

EPUB 的本质是「按约定组织的 zip 包」：`mimetype` + `META-INF/container.xml` +
OPF 清单 + XHTML 正文。解包、读 XML、拼 XML 都是标准库能做的事。

### 读取的三个关键决策

**① 按 spine 读，不按文件名读。**  
spine 是出版方在 OPF 里声明的阅读顺序。文件名（`ch01` / `part-a` / `chapter_final_v2`）
是制作工具的习惯，不保证顺序。按文件名排会把书读乱——这是 EPUB 处理最常见的错误。

**② 目录标题用来补正文缺失的标题。**  
很多 EPUB 的章节文件里没有 `<h1>`，标题只存在于 nav.xhtml / toc.ncx。
不补的话，读出来就是一堆没有层级的段落，AI 导读的结构地图也会是空的。
补齐规则：正文首块不是标题时，用目录里的标题生成一个 H1。

**③ 失败要降级，不要整体失败。**  
一本 30 章的书第 17 章解码失败，正确行为是输出其余 29 章 + 一条警告。
只有「一个可读章节都没有」才整体报错。

### 写出的两个关键决策

**① 按一级标题分章。**  
EPUB 阅读器的目录树来自章文件。整本书塞进一个 xhtml，目录只剩一条，
翻页也慢。没有一级标题的文档退化为单章。

**② mimetype 必须是第一个条目且不压缩。**  
这是 EPUB 规范的硬要求，部分阅读器（尤其老版本）不满足就直接判定文件非法。
用 `zipfile.ZipInfo` + `compress_type=ZIP_STORED` 显式控制。

### 图片处理

`html_to_doc` 新增可选参数 `image_resolver(src, alt) -> ImageRef | None`：

- EPUB 读取时传入解析器，`<img>` 变成真正的图片块，图片从 zip 取出落到临时目录
- 不传时维持原行为（只保留 alt 文本），HTML 读取完全不受影响

这样避免了两套 HTML 解析器，也保证既有行为零变化。

## 三、进度：为什么改千分制

### 问题

原进度条的范围是「任务个数」，`setValue(value + 1)`。一个 300 页的扫描 PDF
从头到尾停在 0/1，OCR 每页 3~6 秒，用户看到的是「进度条不动」——这与卡死无法区分。

### 方案

三层解耦：

```
读取器   progress(done, total, label)     # 自己这一份的进度，如第 137/300 页
   ↓ pipeline._wrap_reader_progress
管线     progress(fraction, label)         # 0~1，当前文件
   ↓ GUI: (index + fraction) / total
界面     千分制进度条 + 「2 / 5　47% · 第 137/300 页」
```

职责分开的好处：读取器不需要知道批次里还有几个文件；界面不需要知道 PDF 还是 EPUB。

**阶段划分**：读取占 0~0.72，写出 0.74，校验 0.96，完成 1.0。读取占大头是因为
OCR 的耗时都在读取段，写出几乎瞬时。

**为什么千分制而不是百分比**：一页 OCR 要几秒，百分比粒度太粗，进度条会一格一格
跳，观感像卡顿。千分制下每页推进约 3‰，是连续的。

### 兼容

`progress` 是可选参数，不传时行为与 2.2 完全一致。测试里专门有一条
「无回调也能转换」。

## 四、AI eye 导读：把「概念」落成文件

### 概念定义

需求原话是「在文档解释相关功能中引入 'ai eye' 概念，其用途是帮助 AI 更好地理解
文字内容」。落到产品上需要一个具体形态，否则「概念」无法交付。

**定义为**：一份与产物同目录的 `<名称>.aieye.md`，是给大模型读的**文档地图**。

为什么不直接给纯文本：大模型读整本书有两个现实问题——上下文放不下；放得下也
有「中间迷失」（Lost in the Middle），对中段细节印象最浅。导读先解决**定位**，
再让模型按需读正文。

### 内容结构

| 部分 | 内容 | 依据 |
|---|---|---|
| front-matter | 来源、格式、字数、段落/标题/表/图数量、生成时间 | 机器可过滤 |
| 结构地图 | 每个标题的层级、位置百分比、该章首段摘要 | 可验证 |
| 插图清单 | 图注 + 文件名 | 可验证 |
| 高频片段 | 字面重复出现的 2~4 字串 | 可验证（统计） |
| 使用建议 | 上下文有限时怎么喂 | 经验规则 |

### 一条刻意的克制：不做语义推断

不引入分词器、不生成 embedding、不调用模型。原因是三重的：

1. **分词有歧义**：「研究生命起源」会被切成「研究生 / 命 / 起源」。导读里给出错的
   术语表，比不给更糟——模型会当真。
2. **体积与许可**：结巴分词等词典方案要带几百 KB 词典，还要处理许可。
3. **离线约束**：本项目的定位是离线工具，导读必须能在没有网络、没有 GPU 的机器上生成。

因此只放**可验证的事实**：结构、位置、字数、图注原文、字面重复串。凡是需要
「理解」才能得出的结论，一律不做。这也让导读的输出是确定的、可复现的。

### 小节编号

空的插图小节、空的高频片段小节会被整节跳过。写死「三、四、五」会出现
「二、」后面直接「五、」，看起来像文件坏了。改成运行时递增编号。

## 五、深色主题：为什么不是反色

### 反色的三个问题

1. **对比度**：`#0F6CBD` 压在深色底上，白字对比度不足；直接反色会得到刺眼的浅蓝
2. **语义色**：完成/跳过/失败的徽标是「前景 + 浅底」成对使用的，反色后前景与底色
   可能撞在一起
3. **层次**：深色下卡片的层次靠「比背景略亮」表达，不是「比背景略暗」

所以做了两套**独立调色板**，共用同一批名字：

| 角色 | 亮色 | 深色 |
|---|---|---|
| 窗口底 | `#F3F3F3` | `#202020` |
| 卡片 | `#FFFFFF` | `#2B2B2B` |
| 正文 | `#1B1B1B` | `#FFFFFF` |
| 强调色 | `#0F6CBD` | `#4CA0E0` |
| 强调色上的文字 | `#FFFFFF` | `#0B1A26` |

注意最后一行：深色下强调色变亮，主按钮上的文字改用深色，而不是继续用白字。

### 工程实现

```python
globals().update(PALETTES[name])   # 覆盖模块全局
app.setPalette(qpalette)           # Qt 内置绘制
app.setStyleSheet(qss())           # 我们自己的样式
```

控件里所有颜色都写 `T.BG` 这种**模块属性访问**，切换后天然拿到新值。
反例是 `from .theme import BG`——那样拿到的是导入时的快照，切换后不更新。

**QPalette 不能省**：只改 QSS 的话，QMessageBox、输入框选区这些 Qt 自己画的
部分仍是白底黑字。

### 踩到的坑：内联样式

查看器的页签原本用 `setStyleSheet` 写内联样式，切换主题后仍是白底——因为那两个
样式串是**类属性**，在模块导入时就求值了。

改成「动态属性 + QSS」：

```python
btn.setProperty("tab", True)
btn.setProperty("active", mode == "md")
repolish(btn)      # 属性变化后必须重新走一遍样式计算，Qt 不会自动匹配
```

顺带把查看器的标题、正文、状态栏全部改成 objectName 驱动，彻底摆脱内联样式。
规则：**凡是随主题变化的样式，一律不写内联。**

### 启动顺序

主题必须在 `MainWindow()` 之前应用，否则会有一帧白底闪烁。`run()` 里先读
QSettings、应用主题、再建窗口。
